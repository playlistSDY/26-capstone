# 주문 점원을 대신하는 에이전트의 업무 범위와 매장 운영 설계

SWitch는 고객이 메뉴를 고르고 주문을 수정하고 결제 단계에 도달할 때까지 주문 점원이 하던 안내와 입력 업무를 맡는 대화형 주문 에이전트다. 메뉴 정보를 길게 읽어 주는 것보다 고객이 원하는 것을 짧은 대화로 파악하고 실제 주문에 반영하는 것이 목적이다. 직원은 반복적인 주문 안내에서 벗어나 음료 제조·상품 제공·현장 운영에 집중할 수 있도록 한다.

이 문서는 현재 데모에서 수행하는 업무와 실제 매장 API 연결 후 가능한 업무, 추가 개발이 필요한 업무를 구분한다. 업무 감소와 이용 편의는 제품의 목표와 기대효과이며, 실제 매장의 직원 개입 시간 감소율이나 주문 완료율을 측정한 실증 결과는 아직 없다.

## 고객 응대의 기본 원칙

주요 고객은 노인과 아이다. 고객에게 주문 상태를 외우도록 요구하지 않고 에이전트가 기억한다. 중간에 말을 바꾸거나 같은 내용을 다시 물어도 현재 주문을 기준으로 응대한다. 나이를 추정해 유아어를 쓰거나 과도하게 설명하지 않고 쉬운 존댓말을 유지한다.

기본 응답은 짧고 구체적인 1~2문장이다. 질문이 필요하면 한 번에 하나만 한다. 고객이 정확한 수치를 묻지 않았다면 당류·카페인·성분 함량을 숫자로 나열하지 않는다. 메뉴 데이터가 자세하더라도 대답은 필요한 내용만 선택한다.

| 고객의 말 | 응대 방향 |
| --- | --- |
| “이거 많이 달아요?” | “꽤 달아요. 덜 달게도 바꿀 수 있어요.” 실제 변경 가능 옵션을 확인한 뒤 안내 |
| “카페인 적은 거 있어요?” | “카페인이 적은 음료로 골라드릴게요.” 조건에 맞는 후보 한두 개 제시 |
| “그거 당이 몇 g이에요?” | 선택한 온도·크기의 당류 수치를 단위와 함께 안내 |
| “우유를 못 먹어요.” | 관련 주의 재료를 짧게 설명하고 우유를 피한 후보를 직접 조회 |
| “내가 뭐 시켰지?” | 실제 담긴 메뉴를 짧게 정리하고 미확정 메뉴는 따로 구분 |
| “잠깐만요.” | “네, 천천히 고르세요.”라고 한 뒤 기다림 |
| “아니, 차가운 걸로요.” | 변경 가능한지 확인하고 반영한 뒤 “차갑게 바꿨어요.” |

위 문장은 말투의 예시다. 메뉴의 실제 옵션이나 성분과 충돌하는 문장을 그대로 사용하지 않는다. 추천은 가능한 후보만 제시하며, 고객이 선택하기 전에는 장바구니에 추가하지 않는다.

## 주문 과정에서 맡는 업무

### 주문 시작과 고객 요구 파악

에이전트는 “무엇을 드시겠어요?”라는 주문 시작부터 매장·포장 선택, 원하는 음료의 종류와 조건 파악을 맡는다. “따뜻한 라떼 두 잔 포장이요”처럼 한 번에 전달한 정보는 모두 사용하고 이미 받은 온도나 수량을 다시 묻지 않는다.

고객이 “뭐가 있는지 모르겠어요”, “너무 달지 않은 거”, “커피 말고 시원한 거”처럼 메뉴명을 모르는 경우에도 조건을 메뉴 후보로 바꾼다. 단순히 전체 메뉴를 읽어 주는 대신 선택 범위를 줄인다. 실제 모델은 앞단 STT 텍스트의 오타·자모 분리·표기 변형을 대화 문맥과 메뉴 검색으로 해석한다. 모든 인식 오류를 해결한다고 보장하지는 않는다.

미리 설정할 정보는 카테고리, 메뉴 별칭, 기본 옵션, 매장·포장 가능 여부, 판매 시간과 품절 상태다. 이 정보가 있으면 직원이 메뉴 위치와 주문 방법을 반복해서 설명하는 일을 줄일 수 있다.

### 메뉴 설명과 비교

각 메뉴의 맛, 주요 재료, 카페인 정도, 당류, 크기와 기본 가격을 안내한다. “라떼랑 아메리카노가 뭐가 달라요?”에는 차이와 선택에 필요한 점만 짚는다. “더 자세히 알려줘”라고 하면 단계적으로 정보를 늘린다.

온도와 크기에 따라 영양 수치가 다른 메뉴는 해당 조합을 사용한다. 디카페인은 카페인이 전혀 없다는 뜻으로 안내하지 않는다. 초콜릿·차·아이스티도 카페인이 있을 수 있으므로 음료 이름만으로 단정하지 않는다.

현재 데모에는 112개 메뉴의 설명·재료·당류·카페인·열량·단백질·포화지방·나트륨·용량·알레르기 주의 정보가 있다. 공식 자료에 맞춘 값과 데모 추정값을 필드별로 구분한다. 배합 예시는 별도의 데모 추정이며 실제 이디야 레시피라는 뜻이 아니다.

### 고객 조건에 맞춘 추천

카페인이 없는 음료, 카페인이 적은 음료, 덜 단 음료, 단 음료, 예산 이하 음료와 피하고 싶은 재료를 조건으로 추천 후보를 조회한다. 동시에 여러 조건을 반영하고 판매 중인 메뉴만 제시한다. 디카페인 추가 금액도 예산 비교에 포함한다.

예를 들어 “커피는 싫고 우유 없는 걸로”라는 요청에는 커피·우유 조건에 맞는 후보를 찾고, “아이랑 같이 먹을 거예요”에는 아이에게도 부담 없이 이해할 수 있는 설명으로 실제 카페인 정보를 확인한 음료를 제안한다. 아이용 제품명만으로 카페인 0을 추정하지 않는다.

현재 당류·카페인 분류는 데모 비교 기준이다. 당류는 한 잔 0g, 15g 이하, 35g 이하, 35g 초과로 나누되, 느껴지는 단맛은 메뉴 종류·향미까지 고려한 별도 추정이다. 제로슈가도 달 수 있어 당류 없음과 안 달다는 구별한다. 카페인은 0mg, 50mg 이하, 150mg 미만, 150mg 이상으로 구분한다. 이 분류는 개인의 건강 안전 기준이나 법적 영양 표시 기준을 의미하지 않는다. 고객에게는 보통 “덜 달아요”, “카페인이 많은 편이에요” 정도로만 안내한다.

추천은 고객이 원하거나 선택에 어려움을 겪을 때 사용한다. 주문이 끝났다고 한 고객에게 추가 상품을 계속 권하거나, 거절한 메뉴를 반복 제안하지 않는다. 매장 추천 상품이 있더라도 고객의 가격·재료·카페인 조건을 우선한다.

### 성분과 알레르기 주의 안내

우유·대두·밀·달걀·복숭아·견과류 등 고객이 말한 주의 재료와 메뉴의 정보를 비교한다. 관련 없는 알레르기 목록을 전부 읽지 않고 해당 재료가 있는지와 다른 후보를 짧게 안내한다. “우유가 들어가요. 우유 없는 음료로 골라드릴게요”처럼 설명과 다음 행동을 연결한다.

불완전한 정보가 있다는 이유로 바로 직원을 찾으라고 하지 않는다. 먼저 공식 표시와 데모 추정의 구분, 기본 레시피, 가능한 대체 옵션, 다른 메뉴를 조회해 선택을 돕는다. 오트밀크로 바꾼다고 다른 재료의 우유까지 사라지는 것은 아니므로 전체 레시피 정보를 확인해야 한다.

현재 데모의 추정값으로 실제 제품의 무알레르기나 안전성을 보장하지 않는다. 교차 접촉 정보가 없는 경우에도 “아무 문제 없어요”라고 말하지 않는다. 운영자가 검증된 재료·교차 접촉 정책·변경 가능한 옵션을 미리 등록할수록 에이전트가 직원 확인 없이 구체적으로 안내할 수 있는 범위가 넓어진다.

### 메뉴 추가와 옵션 선택

메뉴 추가, 온도·크기·샷·시럽·우유 대체·얼음 양·당도·디카페인 선택, 매장·포장 선택을 처리한다. 온도·사이즈·얼음·당도 중 해당 음료에서 선택할 수 있는 중요 옵션은 하나씩 확인한다. 이미 지정한 값은 다시 묻지 않고, 고객이 나머지는 기본으로 해 달라고 위임하면 추가 질문을 생략한다. 미확정 메뉴는 장바구니와 분리해 기억한다.

병음료처럼 수량만 바꿀 수 있는 메뉴, 차갑게만 가능한 음료, 샷을 추가할 수 없는 음료 등 제약을 검사한다. 지원하지 않는 옵션을 적용한 것처럼 응답하지 않는다. 옵션 추가 금액이 있으면 서버가 계산한 결과를 기준으로 안내한다.

현재 데모는 시제품의 고정 옵션 규칙을 사용한다. 매장별 옵션 그룹과 조합 제한을 동적으로 받는 구조는 키오스크 API 명세에 포함했으며 실제 연결은 후속 작업이다.

### 주문 변경과 취소

“하나 더”, “한 잔만”, “방금 거 빼 줘”, “라떼를 아메리카노로 바꿔 줘”, “추가 샷은 취소해 줘”를 현재 주문의 변경으로 처리한다. 전체 취소와 특정 항목 취소를 구별한다. 전체 주문을 비우는 도구도 제공한다.

같은 라떼 두 잔 중 한 잔만 따뜻하게 바꾸는 요청은 항목 분리로 처리한다. 다른 한 잔이나 다른 메뉴의 옵션을 함께 바꾸지 않는다. 수량을 하나 줄이는 것과 해당 메뉴를 전부 삭제하는 것도 구별한다.

“아까 거”가 두 메뉴 중 어느 것을 뜻하는지 모호할 때에는 대상만 확인한다. 명확한 요청을 실행할 때마다 “변경해도 될까요?”를 붙이지 않는다. 도구 성공 결과를 받은 뒤 변경 사실을 짧게 알린다.

### 현재 주문 확인과 기억 도움

고객이 기억하지 못하거나 변경이 겹치면 현재 메뉴와 관련 옵션을 짧게 정리한다. 매번 전체 주문을 읽지 않는다. “라떼는 차갑게, 아메리카노는 그대로예요”처럼 방금 수정한 부분을 중심으로 말한다.

확정된 장바구니, 추천만 한 후보, 필수 옵션이 아직 빠진 요청을 구별한다. 고객이 고민하는 동안 이전 주문을 지우지 않고, 잠깐 멈췄다고 주문 종료나 결제 동의로 해석하지 않는다.

이 기능은 고객의 반복 설명과 직원의 재확인 부담을 줄이는 것을 목표로 한다. 실제 감소 효과는 이용자 테스트에서 확인해야 한다.

### 품절 안내와 대안 제시

품절 메뉴와 재고 부족을 도구로 확인하고 지금 가능한 비슷한 메뉴·옵션을 제시한다. “그건 안 돼요”로 응대를 끝내지 않는다. 고객이 달콤한 우유 음료를 찾다가 품절을 만났다면 같은 조건의 다른 메뉴를 먼저 찾는다.

현재 데모는 카탈로그의 품절 표시와 가상 품목 재고를 검사한다. 실제 잔 수 재고, 옵션 품절, 공용 원재료 소진, 판매 시간 제한은 API 연결 후 서버에서 받아야 한다. 에이전트가 재고 수량을 모르면 임의의 잔 수를 만들어 말하지 않는다.

### 주문 종료 확인과 결제 화면 진입

“이걸로 끝”, “그렇게 할게요”, “결제할래요”를 마무리 의도로 파악한다. 메뉴·옵션·수량·매장/포장·금액을 확인한 뒤 새로운 사용자 동의를 받아 결제 화면으로 이동한다. 온도를 묻는 질문에 대한 “네”를 전체 주문 동의로 사용하지 않는다.

최종 안내 도중 끼어들었거나 주문이 바뀌면 이전 동의를 무효화한다. 음성을 켰을 때는 최종 확인 안내 전체의 재생 완료를 받은 뒤 동의를 활성화한다. 음성을 끄면 화면에 표시된 전체 텍스트를 기준으로 확인한다.

에이전트는 현재 데모의 결제수단 선택 화면까지 연결한다. 실제 카드 승인, 결제 자격정보 입력, 결제 후 환불·취소, 현금 정산은 구현 범위에 포함하지 않는다. “결제 화면으로 이동했어요”와 “결제가 완료됐어요”를 구별한다.

## 대화 중 끼어들기와 음성 안내

고객은 에이전트가 말하거나 답변을 만드는 중에도 새 메시지를 보낼 수 있다. 새 메시지는 이전 응답 생성과 음성 재생·대기열을 중단하고 최신 주문 상태를 확인한 뒤 처리한다. 중단 전에 성공한 주문 변경은 유지한다.

채팅 모달은 텍스트 스트리밍을 표시하고 완성된 문장을 순서대로 음성으로 읽는다. OpenAI Realtime 음성 모델은 안내문 낭독을 담당하며, 주문 판단과 도구 호출은 GPT-6.2 Sol이 담당한다. 브라우저 내장 음성으로 자동 대체하지 않는다.

현재 끼어들기는 ‘말 끊기’ 버튼 또는 새 텍스트 전송으로 시험한다. 마이크가 발화 시작을 감지하는 기능과 STT 자체는 이번 에이전트에 포함하지 않는다. 향후 앞단에서 같은 중단 이벤트를 보내면 이 경로를 연결할 수 있다.

## 직원 대신 이 에이전트를 사용할 이유

### 반복되는 안내를 주문 흐름 안에서 처리

직원은 같은 메뉴의 설명, 옵션 차이, 주문 방법과 수정 방법을 반복해서 안내해야 할 수 있다. 에이전트는 매장 정보를 기반으로 설명과 입력을 함께 처리하므로 고객이 안내를 듣고 다시 화면에서 같은 동작을 찾아야 하는 부담을 줄인다.

효과를 확인하려면 주문 한 건당 직원이 개입한 횟수와 시간, 직원이 제조 작업을 멈춘 횟수, 고객이 다시 설명한 횟수를 측정한다. 에이전트 설치만으로 인건비가 일정 비율 감소한다고 약속하지 않는다.

### 메뉴명이 불명확해도 선택을 도울 수 있음

고객이 상품 이름을 몰라도 “우유 없는 따뜻한 음료”, “덜 달고 커피 아닌 것” 같은 요구를 조합해 후보를 찾는다. 운영자가 메뉴 정보를 미리 등록하면 직원 개개인의 기억에만 의존하지 않고 같은 정보로 안내할 수 있다.

고객에게는 선택지가 줄어드는 편의가, 매장에는 반복 문의가 줄어드는 효과가 기대된다. 이를 확인하려면 추천 후 실제 선택까지의 대화 수와 부적합 추천 비율을 본다.

### 변경 요청을 처음부터 다시 시작하지 않고 처리

주문 중 마음을 바꾸는 것은 흔한 흐름으로 취급한다. 에이전트는 현재 주문을 기억해 해당 항목만 바꾸고 나머지는 유지한다. 직원이 다시 장바구니 전체를 파악하거나 고객이 주문을 처음부터 반복하는 상황을 줄이는 것이 목표다.

### 고객별 설명량과 속도를 조절

고객이 단순히 “달아요?”라고 묻는 경우와 영양 수치를 요구하는 경우에 다르게 답한다. 한 번에 한 질문만 하고 필요할 때 현재 주문을 짚어 줌으로써 노인·아이의 기억 부담과 선택 부담을 줄이는 방향으로 설계한다.

### 검증된 정보와 규칙을 일관되게 적용

매장 옵션·품절·가격 정보를 같은 도구로 조회하고 실행 결과를 확인한다. 지원하지 않는 옵션을 약속하거나, 오래된 가격을 기억으로 말하거나, 결제 전에 주문을 확인하지 않는 오류를 줄일 수 있도록 한다. 실제 정확도는 대화 평가와 API 통합 테스트로 검증한다.

## 미리 설정한 정보로 요구를 구체화하는 예시

### 우유를 피하면서 덜 단 음료를 원하는 고객

고객이 “우유는 못 먹고 너무 단 것도 싫어요”라고 말하면 피할 재료와 당류 조건을 함께 검색한다. 가능 후보를 찾은 뒤 “우유 없는 차로 골라드릴게요. 따뜻한 걸로 드릴까요?”처럼 선택에 필요한 질문 하나만 한다. 원치 않은 영양표 설명으로 대화를 늘리지 않는다.

정확한 응대를 위해서는 우유 대체 가능 여부만이 아니라 크림·초콜릿·소스 등 다른 재료의 우유 표시도 필요하다. 해당 정보가 미리 등록되어 있으면 단순히 “오트로 바꾸면 돼요”라고 잘못 안내하는 일을 줄일 수 있다.

### 예산과 카페인을 함께 고려하는 고객

고객이 “5천 원 안 넘고 카페인 적은 거요”라고 하면 기본 가격과 디카페인 추가 금액까지 계산한 후보를 조회한다. “이 메뉴는 카페인이 적고 예산 안에 들어요”처럼 설명하고, 가격 숫자를 묻거나 선택을 확정할 때 금액을 짚는다.

### 옵션을 여러 번 바꾼 고객

처음에는 라떼 두 잔을 같은 옵션으로 담았다가 “하나는 차갑게, 그건 덜 달게”라고 하면 선택 대상을 유지해 한 잔만 분리한다. 변경 후에는 “한 잔만 차갑게, 덜 달게 바꿨어요”처럼 관련 부분을 알려 준다. 실제로 당도 변경이 지원되는 메뉴인지도 검사한다.

### 품절을 만난 고객

고객이 원한 메뉴가 품절이라면 “지금은 그 메뉴가 없어요. 비슷한 맛으로는 이 메뉴가 있어요”라고 가능한 대안을 제시한다. 등록된 맛·재료·가격·재고 정보가 있어야 단순한 무작위 추천을 피할 수 있다. 고객 동의 없이 대체 메뉴를 담지 않는다.

## 직원 개입을 최소화하는 운영 기준

메뉴·추천·가격·재료 질문에 대한 기본 행동은 조회와 설명이다. 주문 변경 실패 시에는 현재 상태를 조회하고, 가능한 옵션 또는 다른 메뉴로 복구한다. 네트워크 타임아웃은 실패 확정으로 취급하지 않고 같은 요청의 결과를 재확인한다.

직원 인계는 고객이 직접 직원을 요청하거나, 반복 복구로도 해결하지 못하는 실제 시스템 장애에 한정한다. 결제 후 환불·법적 분쟁·실물 장비 고장처럼 주문 에이전트에 권한이나 수단이 없는 업무를 수행했다고 주장하지 않는다.

인계가 필요해도 고객에게 처음부터 다시 설명하게 하지 않는다. 현재 주문, 이미 반영된 변경, 실패한 작업, 미확정 요청을 정리한다. 현재 데모는 이 자료를 만드는 단계이며 실제 호출 시스템에 알림을 보냈다고 표시하지 않는다.

## 구현과 문서를 함께 유지하는 방법

업무 도구를 추가하거나 실제 API를 연결하면 이 문서의 업무 설명과 연결 수준을 함께 갱신한다. 메뉴 데이터는 수집 날짜·공식 ID·출처 URL·추정 여부를 유지하고, 레시피나 옵션이 바뀌면 관련 추천·알레르기·금액 검증도 점검한다.

상세한 데이터가 추가되었다는 이유로 기본 응답을 길게 만들지 않는다. 데이터가 많아질수록 고객에게 필요한 한두 가지를 정확하게 선택하는 것이 목표다.
