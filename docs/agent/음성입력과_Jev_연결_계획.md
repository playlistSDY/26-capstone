# ESP32 음성 입력과 Jev 판단 계층 연결 계획

2026-11-22 상태 갱신: 아래는 원래 목표 설계다. 현재 ESP32 수음·STT·로컬 VAD·동적 소음 문턱·발화 합치기·의미 필터를 독립 CLI에 구현했다. [시제품 구현과 검증 범위](음성입력_필터_시제품.md)를 참조한다. Jev 실제 호출, AEC와 주문 에이전트 통합은 아직 미검증/미구현이며 아래 목표 구조를 모두 완료한 것은 아니다.

이 문서는 앞단 음성 입력의 후속 구현 계획이다. 현재 작업에서는 마이크 수집·STT·VAD·AEC·Jev 호출을 구현하거나 실행하지 않는다. 주문 에이전트에는 계속 최종 텍스트가 들어오며, 기존 텍스트 채팅·음성 출력·수동 끼어들기를 유지한다.

요구사항은 에이전트 대화가 켜진 동안 ICS-43434 마이크를 계속 수음하고, 별도 호출 키워드 없이 손님에게 자연스럽게 응답하는 것이다. 사용자가 말한 Jev는 TypeSafe AI의 의사결정용 모델이며 VAD의 다른 이름이 아니다.

전체 배치와 네 가지 분기는 [시스템 아키텍처](시스템_아키텍처.md)를 기준으로 한다. Jev를 STT 다음의 별도 발화 필터로 명시하며, 전달·무시·대기·중단을 분리한다.

## 권장 구성

ICS-43434와 ESP32 → PC의 오디오 수신·시각 정렬 → 재생 참조를 사용한 에코 제거 → 소음 처리와 VAD → 스트리밍 STT → 대화 상태와 Jev 판단 → 주문 에이전트의 텍스트 입력.

대화가 활성화된 동안 계속 수음하되, 모든 소리를 항상 주문 에이전트에 보내지 않는다. 로컬에서 말소리 구간을 구분하고, 입력 텍스트가 실제 대화 대상인지 판단한 뒤 전달한다. 원본 음성을 영구 저장하는 것은 기본 요구사항으로 추가하지 않는다.

기존 하드웨어 코드는 48kHz·모노·16비트 PCM을 USB 시리얼로 전달하는 테스트다. USB 마이크 장치로 등록되는 구조가 아니므로, 브라우저의 getUserMedia에 echoCancellation 옵션을 넣는 것만으로 현재 시리얼 PCM에 에코 제거가 적용되지는 않는다. PC 수신 경로의 오디오 전처리 계층이 필요하다. [기존 오디오 모니터 설명](../../hardware/kiosk_audio_monitor/README.md)

## 단계별 역할

| 단계 | 판단하거나 처리할 것 | 대신 해결하지 않는 것 |
| --- | --- | --- |
| 오디오 수신 | 프레임 순서·CRC·누락·샘플레이트·시각 | 발화 의미 |
| AEC | 스피커에서 나온 자기 음성을 마이크 입력에서 줄임 | 옆 사람의 실제 대화 제거 |
| 소음 처리와 VAD | 말소리 구간과 시작·종료 후보 | 키오스크에 한 말인지 판단 |
| STT | 음성을 부분·최종 텍스트로 변환 | 주문을 실행할지 결정 |
| 발화 대상 판단 | 키오스크 대화인지, 옆 사람에게 한 말인지 | 화자 방향·거리 같은 음향 증거를 새로 만들어 내기 |
| 턴 종료 판단 | 문장이 끝났는지 더 말할 것인지 | 실제 주문 최종 동의 |
| 주문 에이전트 | 메뉴·옵션·수량·추천·확인·도구 실행 | 음성 장치 제어 |

OpenAI의 VAD는 말하기 시작·종료 이벤트를 제공하고, semantic VAD는 의미에 따라 발화가 끝났는지 판단하는 기능이다. 키오스크에 한 말인지 판단하는 전용 필터로 해석하지 않는다. 모델에 따라 턴 감지 지원 방식도 달라지므로 STT 모델을 정할 때 별도로 확인한다. [공식 VAD 안내](https://developers.openai.com/api/docs/guides/realtime-vad)

## 먼저 해결할 자기 음성 재입력

TTS를 마이크가 다시 받아 “라떼 한 잔”을 손님의 새 주문으로 해석하는 문제를 우선 막아야 한다. TTS 중에 마이크를 완전히 끄는 방식은 사용자의 상시 수음·끼어들기 요구와 맞지 않는다. 재생과 수음을 함께 유지하면서 스피커 참조 신호를 쓰는 AEC를 검토한다.

WebRTC의 오디오 처리 모듈은 수음 스트림과 재생 방향의 참조 스트림을 별도로 받는 인터페이스를 제공한다. 적용 후보이며 현재 장비에서 효과를 검증한 것은 아니다. [WebRTC 공식 오디오 처리 인터페이스](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h)

참조는 단순 TTS 문장이나 원본 파일만으로 충분하지 않다. 실제 출력한 PCM, 볼륨, 재생 시각, 중간 정지와 대기열 폐기까지 맞춰야 한다. 현재 TTS는 24kHz PCM이고 마이크 수신은 48kHz이므로 처리 지점의 샘플레이트와 지연을 정렬한다. 브라우저 출력과 PC 수신이 분리되면 렌더 참조·시각을 전달할 통로도 설계해야 한다.

첫 실험에서는 스피커·마이크 위치와 볼륨을 고정하고, 자기 음성만 재생할 때의 오검출과 손님이 동시에 말할 때의 검출을 나누어 측정한다. 말소리가 크다는 이유만으로 항상 손님이라고 판정하지 않는다.

## Jev를 넣을 위치와 질문

Jev에는 오디오를 직접 보내는 전용 음성 필터라는 가정을 하지 않는다. STT 텍스트와 대화 상태를 구조화해 판단을 요청하는 발화 필터로 설계한다. 실제 호출과 한국어 평가·통합은 예정이며, 명확한 문맥의 규칙 처리와 대체 분류기는 비교 평가 대상으로 둔다. TypeSafe는 state와 typed questions를 받아 구조화된 결과를 반환하는 모델로 설명한다. [공식 소개](https://docs.typesafe.ai/introduction)

질문 하나를 “주문과 관련 있나요?”로 만들지 않는다. 메뉴 이야기라도 동행자에게 한 말일 수 있고, “네”처럼 메뉴 단어가 없어도 직전 질문에 대한 답일 수 있기 때문이다. 다음 판단을 분리한다.

| 판단 | 구분할 내용 |
| --- | --- |
| 대화 대상 | 키오스크 / 동행자·다른 사람 / 판단 어려움 |
| 대화 연결 | 직전 질문의 답 / 새 요청 / 자기 정정 / 무관한 말 |
| 발화 완료 | 아직 이어 말하는 중 / 이번 발화 종료 / 판단 어려움 |
| 끼어들기 의도 | 현재 안내 중단 요청 / 이어지는 짧은 반응 / 무관한 말 |

state에는 현재 STT 부분·최종 텍스트, 직전 질문과 기대 답변 종류, 현재 주문 단계, 최근 짧은 대화, TTS 재생 여부와 실제 들려준 범위, 발화 시간, 전처리가 제공한 음향 신호를 넣는다. 메뉴 전체나 전체 대화를 매번 전송하기보다 이 판단에 필요한 상태를 압축한다.

Choice는 선언한 선택지별 확률과 confidence를, Noul은 0~1의 값을 반환한다. Noul에 별도의 confidence가 있다는 가정을 하지 않는다. 필요한 질문은 한 요청에 묶되 각 판단 결과를 코드에서 조합한다. [Choice](https://docs.typesafe.ai/primitives/choice), [Noul](https://docs.typesafe.ai/primitives/noul)

confidence는 확률 분포를 요약한 값이며 그 숫자 자체가 실제 정답률은 아니다. 키오스크용 한국어 사례로 평가해 판단별 기준을 조정해야 한다. Jev 점수로 실제 결제 승인·성공 여부를 결정하지 않는다. 자연스러운 진행 동의는 대화 문맥으로 처리하며 반복 확인 게이트를 추가하지 않는다. [공식 신뢰도 설명](https://docs.typesafe.ai/confidence)

## 판단 결과를 행동으로 연결하는 방법

### 대화가 명확하게 이어지는 경우

“따뜻하게 드릴까요, 차갑게 드릴까요?” 직후의 “차갑게요”, 수량 질문 뒤의 “두 개요”처럼 문맥이 명확한 경우에는 짧은 응답이라는 이유로 버리지 않는다. 규칙으로 충분한 경우와 Jev를 거치는 경우를 비교해 불필요한 원격 판단을 줄이는 경로를 검토한다.

결제수단 화면 진입도 [반복 확인을 줄이는 정책](확인_반복을_줄이는_정책.md)을 따른다. ‘그래’, ‘맞아’ 같은 동의를 문맥으로 처리하고 요약 낭독·전달 ACK·새 발화 여부·확인 토큰을 필수 조건으로 두지 않는다. 실제 청구 결과는 리더기·결제사 상태로 확인한다.

### 대화 대상이 명확하게 다른 사람인 경우

응답하거나 주문을 변경하지 않는다. 주문 상태는 유지하고 다음 발화를 기다린다. 관련 없는 말이 들릴 때마다 “키오스크에 하신 말씀인가요?”를 반복해 주변 대화에 끼어들지 않는다.

### 애매한 경우

부분 텍스트라면 뒤에 오는 발화를 조금 더 기다려 하나로 판단한다. 끝까지 모호하고 주문 변경이 필요하다면 “라떼 한 잔을 더 담을까요?”처럼 필요한 한 가지만 확인한다. 모호한 모든 발화에 무조건 질문하지는 않는다.

대상을 판단할 증거가 충분하지 않으면 텍스트만으로 확정할 수 없다. 단일 마이크에 같은 말과 비슷한 음향으로 들어온 손님·동행자의 발화를 100% 구분하는 것은 보장하지 않는다. 설치 위치·거리·수음 방향과 대화 상태를 함께 개선해야 한다.

## 끼어들기의 두 단계

Jev의 네트워크 응답을 기다린 다음 음성을 멈추는 구조는 피한다. 즉각적인 사용자 경험과 실제 주문 실행 결정을 분리한다.

1. 에코 제거 후 가까운 사람의 발화 후보를 빠르게 잡으면 TTS를 부드럽게 낮추거나 잠시 멈춘다. 새 주문 변경 실행도 잠정 보류한다. 이 단계에서는 음성이 확정된 새 주문이라고 간주하지 않는다.
2. STT와 문맥 판단으로 실제 끼어들기임이 확인되면 기존 생성·재생 대기열을 취소한다. 중단 자체를 이유로 주문 확인과 동의를 다시 요구하지 않는다. 이미 성공한 도구 변경은 조회해 보존한다. 최종 텍스트를 새 턴으로 보낸다.

기침·주변 소리·다른 사람의 발화였으면 멈춘 지점에서 안내를 이어가는 방식을 검토한다. 현재 수동 ‘말 끊기’는 즉시 취소이며, 이 문서의 잠정 일시정지·재개는 아직 구현하지 않았다.

## 발화 도중 실행하면 안 되는 이유

“라떼 두 잔… 아니 한 잔”에서 부분 텍스트만 보고 두 잔을 추가하면 정정과 중복 변경이 발생한다. STT 부분 결과는 화면 표시·판단 준비에 활용하되, 장바구니 변경은 발화 종료와 최종 텍스트를 기준으로 실행한다. 읽기 전용 메뉴 검색은 미리 준비할 수 있지만 결과가 확정되지 않은 요청을 주문으로 반영하지 않는다.

STT가 이미 완료한 문장을 수정해서 보내는 경우에는 같은 utterance_id의 revision을 올린다. 메시지를 새 주문으로 추가하지 않는다. 이미 실행된 요청이면 작업 결과를 조회하고 수정 의도를 해석하는 절차가 필요하다.

## 앞단과 주문 에이전트 사이의 제안 이벤트

| 이벤트 | 주요 필드 | 사용처 |
| --- | --- | --- |
| session.audio_started | session_id, capture_clock | 활성 대화의 입력 시작 |
| speech.candidate_started | utterance_id, started_at, acoustic_evidence | 잠정 음성 낮춤·일시정지 |
| transcript.partial | utterance_id, revision, text | 부분 표시와 판단 준비 |
| transcript.final | utterance_id, revision, text, finished_at | 관련성·대상 판단 |
| turn.accepted | utterance_id, reply_to_message_id, decision_summary | 주문 에이전트 입력 |
| turn.ignored | utterance_id, reason_class | 주문 변경 없이 대기 |
| turn.clarification_needed | utterance_id, ambiguous_target | 필요한 한 가지 확인 |
| user.interrupted | utterance_id, playback_offset | 기존 응답 취소와 최신 주문 조회 |
| session.audio_stopped | session_id | 입력 종료와 남은 버퍼 정리 |

event_id와 sequence로 중복·역전을 감지한다. 발화와 세션의 소유 관계를 확인하고, 과거 고객의 늦은 발화를 새 고객 주문으로 적용하지 않는다. 앞단 판단의 확률 필드는 실제 API 응답을 확인한 뒤 매핑하며 이 표를 Jev API 스키마로 오해하지 않는다.

## 대안 비교와 선택 의견

| 대안 | 장점 | 확인할 점 |
| --- | --- | --- |
| VAD와 문맥 규칙 | 로컬에서 빠르고 비용이 적으며 명확한 짧은 답을 처리하기 쉬움 | 동행자 대화·모호한 표현의 일반화가 약함 |
| Jev 판단 계층 | 대상·연결·종료·끼어들기를 구조적으로 분리하는 용도에 맞음 | 한국어·시니어·아이 발화 정확도, 국내 왕복 지연, 별도 서비스 의존성 |
| 작은 LLM의 구조화 분류 | 기존 OpenAI 환경과 평가 도구를 재사용하기 쉬움 | 같은 과제에서의 실제 지연·비용·오탐·누락을 비교해야 함 |
| 오디오·대화 통합 실시간 모델 | 음향·문맥·턴 처리를 함께 사용하는 후보 | 현재 STT 텍스트 에이전트와의 역할 분리, 권한·검증 구조 재설계 |

권장 실험은 AEC와 VAD를 기본으로 두고, 명확한 문맥은 가벼운 경로로 처리하며 모호한 발화에 Jev를 적용하는 구성이다. 비교 실험에서는 모든 발화를 Jev에 보내는 방식도 기준선으로 둔다. 처음부터 Jev를 모든 오디오 프레임이나 STT 토큰마다 호출하지 않는다.

TypeSafe가 발표한 70~500ms 응답 시간은 공급자 측 사례이며, 서부 미국 환경의 측정이라는 설명이 있다. 국내 키오스크에서의 지연으로 보장하지 않는다. 실제 환경에서 p50·p95 지연과 앞단 전체 지연을 측정한 뒤 선택한다. [공식 출시 설명](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

## 평가와 구현 순서

평가에는 명확한 주문, “네/아니요” 같은 짧은 답, 긴 생각 시간과 중간 멈춤, 한 발화의 정정, 동행자와 메뉴 이야기, TV·음악·다른 고객 대화, TTS 자기 재입력, TTS와 고객의 동시 발화, 기침·웃음, 여러 사람이 동시에 말하는 상황을 넣는다.

측정은 키오스크 발화를 놓친 비율, 주변 대화를 잘못 받은 비율, TTS의 자기 반응 횟수, 잘못된 중단·재개, 발화 시작부터 음성이 낮아지는 시간, 발화 종료부터 첫 안내까지의 시간, STT 수정으로 인한 중복 주문과 전체 비용을 본다. 평균만 보지 않고 느린 사례도 함께 본다.

구현 순서는 오디오 시각·품질 확인, 재생 참조와 AEC, 로컬 VAD와 짧은 사전 버퍼, STT 이벤트, 데이터 수집·라벨링, Jev와 대안의 비교, 두 단계 끼어들기 순으로 제안한다. 200~300ms 정도의 사전 버퍼는 첫소리 유실을 줄이기 위한 초기 실험 후보이며 장비 측정으로 조정한다.

현재는 위 계획만 문서화했다. TypeSafe SDK·키·네트워크 호출을 추가하지 않았고, 마이크·ESP32 코드와 STT 입력 경로도 수정하지 않았다.
