# 화면 하이라이트와 상황에 맞춘 조작 안내

2026-11-22. 대화의 설명 대상과 실제 화면 요소를 연결한다. 직접 누르라는 요청이 없어도 에이전트가 메뉴·옵션·수량·결제를 설명할 때 해당 요소를 표시한다. 고령자·아이를 포함해 키오스크에 익숙하지 않은 손님이 직접 해 보거나 필요한 작업만 맡길 수 있게 한다.

## 사용자 경험

기본 동작은 에이전트의 직접 처리다. 수량·옵션 변경과 결제 요청을 받으면 기존 도구로 처리하며 버튼 안내만으로 넘기지 않는다. 하이라이트는 설명·질문의 보조 수단이다. 사용자가 직접 선택하려는 의사가 있을 때 조작 안내와 대기로 연결한다. 단순히 번거로워한다는 이유만으로 직접 조작을 요구하지 않는다.

- “큰 크기는 500원 추가예요” → 해당 음료 옵션 창을 열고 큰 크기 버튼을 강조한다. 설명만으로 큰 크기를 선택하지 않는다.
- “얼음은 적게 넣어드릴까요?” → 해당 음료와 얼음 항목을 표시한다. 말로 동의하거나 화면에서 고른 결과를 주문에 사용한다.
- 메뉴 추가 도구가 옵션 대기 상태를 반환하면 그 음료의 수량·옵션을 유지한 창과 현재 질문 항목을 자동 표시한다. 다른 설명 대상은 에이전트의 명시적 하이라이트를 우선한다.
- 에이전트가 장바구니에 담은 뒤에는 수량·옵션 버튼의 위치 안내와 “표시된 버튼을 누르거나 결제해줘라고 말씀해 주세요”를 화면에 보여 준다. 설명 대상에 맞춰 강조를 이동하며 별도의 위치 안내 버튼 패널을 만들지 않는다.
- 손님이 귀찮아하거나 직접 하려는 문맥이면 “원하는 옵션을 고른 뒤 담기를 눌러 주세요”처럼 연결하고 기다린다. 고정된 질문 순서나 매 클릭 후의 추가 질문을 강제하지 않는다.
- 채팅·음성으로 말한 ‘사용법 알려줘/다음 단계 알려줘’는 최신 화면을 포함한 실제 대화 요청이다. 별도 상시 안내 패널과 사용법·위치·위임 버튼은 표시하지 않는다. ‘대신 해줘’는 직전 안내 목표와 현재 편집 내용을 함께 전달해 기존 주문 도구로 이어진다. 미지정 필수 선택과 모호한 대상만 짧게 해결한다.
- 실제 결제 승인 여부는 기존 결제 장치·데모 결과를 따른다. 카드 버튼 설명은 리더기 시작이나 청구가 아니다.

## 에이전트 판단에 쓰는 정보

최근 대화·말투·명시적 의사·직접 조작을 종합한다. 현재 입력은 STT 이후의 텍스트이므로 ‘말투’는 표현과 대화 흐름에서 판단하며 음성 억양을 분석한다고 주장하지 않는다. 나이·장애·숙련도를 수치 하나로 단정하지 않는다.

`ui_context.interaction`은 세션 안에서만 유지하는 화면 조작 지표다. 브라우저가 실제 키오스크 버튼의 클릭·키보드 활성화를 세며 에이전트의 도구 실행이나 안내를 위한 자동 이동은 세지 않는다.

| 필드 | 의미 |
| --- | --- |
| activations | 실제 키오스크 버튼 활성화 누적 횟수 |
| option_changes | 옵션 버튼 활성화 횟수. 이미 선택된 값을 다시 누르는 경우도 포함 |
| screen_changes | 카테고리·메뉴·뒤로·결제·이용 방법 등 이동 관련 버튼 활성화 횟수. 실제 화면 전환 횟수와는 구별 |
| guidance_completed | 표시 대상에 포함된 버튼을 직접 누른 횟수. 학습 성취도나 작업 성공률이 아님 |
| recent_actions | 최근 조작 종류 최대 12개 |
| idle_ms | 마지막 직접 조작부터 요청 전송까지의 경과 시간. 없으면 생략 |
| session_elapsed_ms | 화면 이용 시작·초기화 이후 요청 전송까지의 경과 시간 |

직접 조작이 잘 이어지고 “내가 할게”라고 했다면 설명을 줄여 기다린다. 반복 이동·긴 멈춤과 “어디 눌러요”가 함께 나타나면 한 단계만 안내한다. “빨리/귀찮아/알아서”와 앞 대화의 위임 의사가 있으면 선택지를 줄이거나 현재 선택을 이어받아 처리한다. 긴 대기만으로 선택을 가로채지 않는다. 최근 명시적 의사를 우선한다.

## 서버 도구와 상태 계약

`guide_ui(target, instruction, product_id?, line_id?, option?, value?)`가 `state.guidance`에 일회성 식별자와 안내를 기록한다. 일반 응답 스트림의 최종 상태에 포함되어 UI에 적용된다. 낭독 완료나 추가 확인 ACK를 기다리는 기능은 아니다.

| target | 필요한 문맥·대상 |
| --- | --- |
| place | 홈 또는 상단 매장·포장 버튼 |
| category | value에 실제 카테고리명 |
| product | product_id로 메뉴 위치 표시 |
| option | product_id, option. value를 주면 개별 버튼, 없으면 옵션 항목 전체 |
| editor.quantity / editor.add | 편집 중인 메뉴 수량 / 담기·수정 버튼 |
| cart.quantity / cart.options / cart.remove | line_id로 장바구니의 특정 항목 지정 |
| checkout / confirm_payment | 주문 확인 진입 / 확인 후 결제수단 진입 버튼 |
| payment.method | 이미 열린 결제수단 화면에서 value=card/samsung/apple/kakao/naver |
| back | 현재 화면의 돌아가기 버튼 |

메뉴·항목·옵션·결제 단계와 지원 여부를 서버에서 검증한다. 임의 CSS 선택자, 화면 좌표, 스크립트는 받지 않는다. 하이라이트는 장바구니·옵션·금액·청구를 변경하지 않는다. 표시를 위한 카테고리 이동과 옵션 창 열기만 준비할 수 있다. 같은 음료를 편집하고 있으면 선택한 옵션과 수량을 유지한다.

`ui_context.guidance`에는 마지막 안내와 showing/done 상태를 전송해 다음 발화의 ‘이거/대신/다음’을 해석한다. 새 턴에서는 서버의 이전 표시 명령을 비우므로 과거 명령을 반복 재생하지 않는다. 기존 요청 ID·세대 검사로 늦은 응답과 취소된 응답이 안내를 덮어쓰지 않게 한다.

## 화면 동작과 접근성

실제 요소의 위치·크기에 맞춘 테두리와 ‘여기예요’ 표식을 표시한다. 화면 밖이면 해당 위치로 이동하며 크기 변경·스크롤·키오스크 배율을 따라간다. 클릭을 가로막는 덮개나 화면 전체의 어두운 배경은 추가하지 않는다. 표시 대상이 없는 경우 현재 위치를 찾지 못했다는 화면 안내를 제공한다.

빠른 점멸 대신 느린 테두리 강조를 사용하고 기기의 동작 줄이기 설정에서는 애니메이션을 끈다. 색상 외에도 표식과 짧은 설명을 제공한다. 버튼 하나를 누르면 안내 완료로, 다른 버튼을 누르면 기존 위치 표시를 해제한다. 다음 대화나 다른 버튼 조작으로 표시를 정리한다. 홈 초기화·세션 종료 시 표시와 조작 지표를 비운다. 원래 화면의 직접 조작과 기존 결제 흐름을 유지한다.

## 검증과 범위

가상 모델을 통한 실제 SDK 도구 호출, 안내 전후 장바구니 불변, 현재 옵션을 이어받는 위임, 조작 지표 정규화, 리더기를 시작하지 않는 결제 안내를 검증한다. 브라우저에서는 옵션 대화의 음료 창 표시, 설명 대상 버튼 강조, 직접 선택·담기, 수량·옵션·결제 위치, 위임 시 선택 보존, 좁은 화면과 동작 줄이기를 검증한다.

STT·Jev·음성 억양 분석이나 사용자 숙련도 분류 모델은 이번 구현에 추가하지 않는다. 안내 수준은 제공된 대화·행동 문맥에 대한 주문 에이전트의 판단이며 실제 매장 사용자 평가와 구별한다.

2026-11-22 검증 결과: Python 106개, 웹 단위 테스트 39개, 관련 브라우저 시나리오 16개를 통과했다. 타입 검사·웹 빌드는 별도 임시 출력 경로에서 통과했다(기존 iCloud dist 정리 충돌을 피함). 데스크톱·390px 화면의 강조 표시도 렌더링해 확인했다. 실제 중앙 모델에서 큰 크기 설명 → 직접 고르겠다는 요청에 담기 버튼 안내 → 현재 선택 그대로 두 잔 위임(큰 크기·얼음 적게·덜 달게, 9,400원)을 확인했다. 중앙 서버와 로컬의 최종 UI·응대 지침 파일 해시가 같은 것도 확인했다. 이는 해당 사례의 확인이며 모든 표현에서의 품질 보장은 아니다.


2026-11-22 후속 수정: 상시 사용법 패널·위치 버튼·‘대신 해줘’ 버튼을 제거했다. 대화 중 해당 실제 화면 요소만 강조한다. 직접 처리 요청에는 기존 도구를 호출하고 완료 결과를 말하며, 사용자가 명시적으로 직접 하겠다고 한 경우에만 조작을 기다린다. 이용 방법만 빠져 있던 결제 흐름에서 ‘먹고 갈래’라고 답하면 같은 턴에 이용 방법을 반영하고 주문 확인·결제수단 화면으로 이어 간다. 하이라이트와 조작 지표는 이 기본값을 바꾸지 않는다.

후속 검증: Python 106개·관련 브라우저 16개와 임시 출력 경로의 웹 빌드를 통과했다. 실제 중앙 모델에서 장바구니가 있고 이용 방법이 미선택인 상태로 ‘다 골랐어 결제할래 → 먹고갈래 → 응’을 실행했다. 각각 이용 방법 질문 → 매장 반영과 주문 확인 화면 → 결제수단 화면으로 진행했으며, 버튼 클릭을 요구하지 않았다. 상시 안내 패널이 없고 실제 버튼 강조가 유지되는 데스크톱 렌더링도 확인했다.
