# 텍스트 기반 주문 대화 에이전트 설계

SWitch 에이전트는 손님이 이전 주문을 외우지 않아도 대화를 이어갈 수 있도록 현재 주문과 미완료 요청을 기억한다. 필요한 때 짧게 진행 상황을 알리고, 확인이 필요한 선택에만 질문한다. 입력은 앞단 STT 결과 텍스트이며, 출력은 안내 텍스트와 도구 실행 결과다.

## 대화 정책

| 상황 | 기본 행동 | 피할 행동 |
| --- | --- | --- |
| 메뉴·온도·수량이 모두 명확함 | 한 번에 반영한 뒤 짧게 안내 | 이미 받은 정보를 순서대로 다시 질문 |
| 주문 필수 정보가 빠짐 | 지금 필요한 질문 하나 | 온도·크기·시럽·샷을 한꺼번에 묻기 |
| 중요 옵션을 언급하지 않음 | 사이즈·얼음·당도 중 해당 메뉴에 필요한 선택만 하나씩 확인 | 동의 없이 기본값으로 담기 |
| 여러 메뉴 또는 수정이 쌓임 | 관련된 주문을 짧게 요약 | 매 턴 전체 주문 읽기 |
| 사용자가 기억을 못 함 | 현재 주문과 미확정 내용을 구별해 설명 | 사용자가 앞 대화를 기억하도록 요구 |
| 추천 요청 또는 고르기 어려움 | 조건에 맞는 판매 가능 후보 한두 개 | 긴 메뉴 나열, 반복 권유, 무조건 비싼 메뉴 추천 |
| 생각 중이거나 대기 요청 | 짧게 응답하고 기다림 | 연속 질문, 침묵을 동의로 처리 |
| 요청 대상이 여러 개 | 대상만 짧게 확인 | 임의의 메뉴를 삭제·변경 |
| 확실한 수정 요청 | 실행 결과를 확인하고 변경 안내 | 매번 변경해도 되는지 다시 질문 |
| 주문 종료 의사 | 미완료 항목 해결 후 최종 요약 | “끝”을 결제 동의로 바로 처리 |

노인·아이에게 쉬운 존댓말을 쓴다. 나이를 자동 추정하거나 유아어·훈계조로 말하지 않는다. 한 번에 한 질문, 보통 1~3문장을 기본으로 하되 손님이 전체 메뉴 설명을 요청하면 필요한 만큼 나눠 읽는다.

현재 실행 지침은 [prompt.txt](../../order-agent/switch_agent/prompt.txt)에 둔다. 대화 규칙을 바꾸면 평가 시나리오의 기대 응답도 함께 갱신한다.

## 처리 흐름과 상태의 소유자

텍스트 입력 → 이전 대화와 현재 주문 조회 → 발화 해석 → 필요한 도구 순차 호출 → 실제 결과 검증 → 짧은 안내 또는 다음 질문 → 새 입력 대기의 반복이다. LLM이 직접 주문 데이터베이스를 수정하지 않는다.

| 상태 | 권위와 보관 방식 |
| --- | --- |
| 메뉴·옵션·가격·재고 | 향후 키오스크 API. 현재는 독립 복사한 시제품 카탈로그와 가상 재고 |
| 담긴 주문과 금액 | 현재 OrderStore. 실제 연결 후 키오스크 장바구니 응답 |
| 대화 이력·추천 후보·미확정 요청 | 대화 이력과 서버 item_drafts. 세션 영속 저장은 후속 단계 |
| 현재 수정 대상 | 장바구니 항목 ID인 focus. 지시어 해석의 참고이며 자동 동의는 아님 |
| 최종 확인 | 서버 주문 버전, 안내 턴, 전달 여부, 만료 시각에 묶인 별도 상태 |
| 결제 | 에이전트는 주문 확인·수단 선택·재시도·승인 전 취소를 요청. 결과는 기존 키오스크 결제 흐름이 제공 |

주문 단계는 ordering, checkout, handoff다. pending confirmation은 ordering 안의 별도 상태다. 미확정 추가는 서버 item_drafts로 구조화하고, 남아 있으면 최종 확인 게이트에서 차단한다. 문맥상 동의 여부는 모델이 해석하므로 실제 발화 평가도 필요하다.

## 가상 도구

| 도구 | 역할 |
| --- | --- |
| search_menu | 이름·유사 표기·카테고리·가격·커피 여부로 후보 조회 |
| read_menu | 메뉴 기본값, 가능 온도, 옵션 제약, 재고·품절·영양·재료·알레르기 확인 |
| find_suitable_menu | 카페인·당류·피할 재료·예산 조건 추천 |
| get_cart | 현재 주문·옵션·수량·합계·선택 항목 조회 |
| add_item | 새 메뉴 추가 |
| cancel_pending_item | 아직 담지 않은 메뉴의 옵션 확인 요청 취소 |
| edit_item | 수량·옵션 변경, 옵션 기본값 복원, 메뉴 교체 |
| split_item | 동일 항목 여러 잔 중 일부의 옵션만 변경 |
| remove_item | 항목 삭제 |
| clear_order | 명시적인 전체 주문 취소 |
| select_item | 수정 대상 선택 |
| set_order_type | 매장·포장 선택 |
| request_final_confirmation | 최종 주문 요약 생성과 새 사용자 답변 대기 |
| open_checkout | 유효한 최종 확인 후 가상 결제 진입 이벤트 |
| select_payment_method | 카드·삼성페이·애플페이·카카오페이·네이버페이 리더기 열기 |
| retry_payment | 실패·시간 초과 후 같은 수단으로 재시도 |
| cancel_payment | 승인 전 시도 취소, 주문 유지 |
| return_to_order | 결제 단계에서 주문 수정 단계로 복귀 |
| handoff_to_staff | 주문과 미해결 사항을 보존한 가상 직원 인계 이벤트 |

검색은 단순 유사도와 부분 일치이며 STT 오류 복구 모델의 성능을 보장하지 않는다. 추천은 검색 도구의 사실을 바탕으로 LLM이 설명한다. 성분·알레르기·카페인은 메뉴 지식 데이터에서 조회한다. 공식 자료와 데모 추정값을 필드별로 구분한다. 일반 응답에는 숫자를 나열하지 않는다.

## 최종 확인과 결제

1. 메뉴·옵션·수량·매장/포장·금액을 도구 상태로 요약한다.
2. 최종 요약을 응답으로 반환한 뒤 전달 완료로 표시한다. CLI에서는 텍스트 반환을 전달로 간주하고 웹에서는 음성 전체 재생 완료 또는 명시적 텍스트 모드로 전달을 확인한다.
3. 다음 사용자 턴에서 직전 요약에 동의해야 한다. 옵션 질문에 대한 “네”로는 통과할 수 없다.
4. 주문 수정, 질문, 확인 만료, 전달되지 않은 요약은 동의를 무효화한다. 최종 확인 도구와 결제 진입 도구를 같은 턴에 호출할 수 없다.
5. 결제 진입 직전에 옵션·품절·재고를 다시 검증한다. 실제 API 연결 후에는 가격 견적과 재고 확보도 서버에서 원자적으로 검사한다.

현재 동의 인식은 “네”, “예”, “좋아요”, “네 결제해주세요”, 직전 최종 확인에 대한 “카드요” 등의 제한된 명확한 표현을 허용하는 보수적인 구현이다. “네, 근데 하나 빼 주세요”는 허용하지 않는다. 다양한 자연어 동의 표현의 포괄성은 아직 부족하며, 후속 버전에서 발화 의도 분류와 실제 전달 메시지 ID를 결합한다. 모델이 open_checkout을 선택했다는 이유만으로 확인을 통과시키지는 않는다.

현재 120초 만료는 개발용 값이며 이용자 테스트로 정해야 한다. 침묵 때문에 주문을 확정하거나 자동 삭제하지 않는다. 실제 음성 출력 연결 시 최종 요약 전체가 재생되었다는 playback.finished 이벤트를 받은 후 확인을 활성화하고, 중간 끼어들기는 무효화해야 한다.

## 중간 안내와 끼어들기 후속 설계

주기적으로 말을 하는 타이머보다 맥락 변화에 반응하는 안내를 우선한다. 확정된 변경은 “라떼는 차갑게 바꿨어요”처럼 알리고, 여러 번 수정했으면 관련 항목을 짧게 정리한다. 대기 요청 이후에는 idle 안내를 중단한다. 고객이 무엇을 골랐는지 묻거나 오래 쉬었다 돌아오면 현재 내역을 다시 안내한다.

후속 전송 계층은 utterance.final, utterance.revised, playback.started, playback.finished, user.interrupted, session.idle, cart.updated, checkout.changed를 받아야 한다. 각 이벤트에 session_id, event_id, sequence와 reply_to_message_id를 넣는다. 중복 발화의 주문 중복 추가 방지는 event_id로, STT 수정본은 원래 utterance_id로 연결한다. 현재 CLI에는 이 이벤트 계층이 없다.

끼어들기가 들어오면 남은 안내 재생을 취소하고, 현재 실행 중인 변경이 완료되었는지 먼저 조회한 뒤 새 요청을 처리한다. 늦게 도착한 이전 턴의 답변은 재생하지 않는다. 네트워크 타임아웃이나 실행 취소가 이미 반영된 주문을 되돌렸다고 가정하지 않는다.

현재 런타임은 세션 내 턴을 순차 실행하고 웹 입력으로 실행 중인 SDK 스트리밍을 취소할 수 있다. 예외가 나도 성공한 가상 도구 변경은 보존하고 확인 상태를 해제하며, 같은 요청을 자동 재실행하지 않도록 기록한다. 웹 모달은 중단 입력·오디오 재생 취소·SDK 텍스트 스트리밍을 연결했다. 마이크 감지와 STT 수정 이벤트는 후속 연동 대상이다.

## 현 구현과 다음 단계

Python 3.14 환경에서 openai-agents 0.25.0을 설치해 실제 SDK Runner와 도구 스키마를 검증했다. CLI와 로컬 HTTP 서버의 메모리 세션이며 종료 시 주문과 이력은 사라진다. API 키는 서버 환경변수 또는 로컬 .env에서만 읽는다. 추적은 기본 비활성화하고 모델 응답 저장 옵션도 끈다. 이는 OpenAI의 모든 처리·보관 정책을 변경하는 설정을 의미하지 않는다.

현재 단계는 가상 도구 기반 프로토타입이다. 다음 단계는 시나리오별 실제 모델 평가, 미확정 주문의 조합별 확장, 세션 저장, 실제 매장 API 연결이다. 웹 브리지는 요청 ID로 중복 실행을 방지하고 끼어들기·재생 확인을 지원한다. 주문 확인 화면부터 수단 선택·리더기·실패 복구·완료 안내까지 기존 데모 UI에 연결했다. 실제 청구·직원 알림은 연결하지 않았다.
